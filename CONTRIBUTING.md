# Contributing to .j Frameworks

The project is in bounded development. Review feedback is most useful when it identifies the exact source commit, work package or batch, expected .NET behavior, observed Java behavior, and the evidence that supports the comparison.

## Proposing a change

1. Read the [current status](README.md) and the relevant [Stage-2 work package](planning/stage-2/README.md).
2. Keep a proposal within one named capability or gate. State whether it changes public API shape, behavior, tests, provenance, licensing evidence, or only documentation.
3. For behavior or API changes, cite the pinned upstream source or oracle, add a bounded fixture when appropriate, and report the commands and results you actually ran. Mark any unrun checks explicitly.
4. Keep reference captures and their hashes intact. Do not silently replace upstream evidence, notices, or generated output. Record new pins and rights questions in the relevant evidence ledger.
5. Do not mark a framework, task, or release complete solely because a local fixture passes. Update the progress ledger only when its stated acceptance criteria are met and reviewed.

The public collaboration channel has not yet been established in this checkout. Until a hosting repository and maintainer contact are confirmed, this document describes the expected content of a review rather than promising an issue, pull-request, or security-response workflow.
